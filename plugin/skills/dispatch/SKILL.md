# 派活给 Gemini / Copilot，Claude 当指挥

## 分工
| 执行者 | subagent_type | 适合 |
|---|---|---|
| Copilot | `dispatch:copilot-worker` | 步骤明确的改代码、补测试、修 bug |
| Gemini | `dispatch:gemini-worker` | 一次读大量代码或日志的分析、第二意见、审查 diff；也可以改代码 |
| Claude（我） | — | 拆任务、写任务说明、审查、解决冲突、合并、最终验证；涉及真机或硬件的步骤自己做 |

用户指定了执行者就按用户的来。

## 前提
- `~/.claude/settings.json` 里要有 `"worktree": {"baseRef": "head"}`，否则 worktree 从远程默认分支建，看不到当前分支的代码。没有就先提醒用户加上。

## 流程
1. **拆任务**：拆成互不重叠的小任务，每个只改一组文件。会改到同一个文件的任务不要并行。
2. **写任务说明**：执行者看不到我们的对话，说明必须能独立看懂：
   - 开头写"改代码"或"只读"
   - 目标，以及为什么要做
   - 涉及的文件和函数（写相对路径）
   - 约束：代码风格、哪些不能改、项目约定（例如不写 C 盘临时目录，不往仓库放内部数据）
   - 验收命令（例如 `pytest tests/test_x.py -q`）和通过标准
3. **派活**：调用 Agent，加 `isolation: "worktree"`。互不相关的任务放在同一条消息里并行发出。
   - worktree 之间不隔离，执行者能读到相邻 worktree 的文件。同一道题不要同时派给两个执行者；要对比时，先派一个，删掉它的 worktree（分支保留）后再派另一个。
   - 任务说明里写明"只能读写当前目录之内的文件"。
4. **审查**：拿到汇报后，自己到它的 worktree 里看 `git diff <起点>..HEAD`，并亲自跑验收命令。不要只信汇报。
   - 核对汇报里的起点是不是当前分支的 HEAD。
   - 只读分析要抽查引用的 `文件:行号`；"某处没有测试 / 没有实现"这类结论要自己 grep 确认。
   - 不合格：把具体问题写成新的任务说明，交给同一个执行者重做，或换一个执行者；同一任务最多重派 2 次，之后我自己改。
   - 可以交叉审查：Copilot 写的代码交给 `dispatch:gemini-worker` 用只读模式审查。
5. **合并**：在主工作区按顺序 `git merge` 或 `git cherry-pick` 各个 worktree 分支，有冲突我来解决；合并后跑一遍完整测试。合并完删除对应的 worktree 和分支。
6. **向用户汇报**：说明每个任务谁做的、结果如何、我改了哪些地方、测试结果。是否 commit 或 push 按用户平时的习惯来。
